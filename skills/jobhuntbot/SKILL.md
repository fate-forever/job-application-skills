# JobHuntBot

把真实候选人证据与真实岗位要求对齐，优化有依据的投递选择，而不是关键词命中、盲目扩量或保证通过率。复用现有资料与工具，按当前请求选择模式，不为一次建议启动完整求职系统。

## 先确定任务边界

- **岗位推荐、排序或诊断**：默认只读。读取相关资料及投递历史，研究官方招聘页面，给出建议；不新增记录、不填表、不替用户投递。阅读 [岗位筛选方法](references/job-screening.md)。
- **记录或核对台账**：核对默认只读；用户要求新增、修正、同步，或已有明确持续记录授权时，才写入有证据的新事件。推荐、打开岗位、收藏、暂存申请均不算投递。
- **网申**：用户要求填写、保存或提交时才进入。阅读 [网申操作](references/application-playbook.md)；中文个人网申如有 `resume-application` 技能，按其资料与复核流程执行。最终提交需要明确授权。
- **搭建求职系统**：用户要求创建画像、规则或台账时，阅读 [初始化流程](references/setup-workflow.md)，复用 `templates/`。普通岗位推荐不需要先初始化这些文件。
- **简历路由**：推荐现有材料版本；只有用户要求优化时才编辑，遵循适用的简历/文档技能。

缺失资料仅在影响当前结论时追问。不要为了推荐国内校招岗位索要地址、家庭、薪资或签证信息；相关硬条件确实出现时再核实。

## 本地资料与证据

先阅读 [私有资料入口与能力边界](references/candidate-context.md)，按用户指定路径读取本次需要的资料。入口文件只描述位置与复用规则，不保存个人履历。

优先使用最新用户确认、当前简历、对应实习记录与已核实运行证据；旧画像中的判断不能覆盖新增事实。资料冲突需说明，不能默默选择更好看的数字。用户对某一家公司的申请选择，不是全局求职偏好。

## 推荐工作流

1. 确认目标：匹配度、相对通过可行性、职业发展或 DDL 优先；复用已知毕业时间、城市偏好与剩余名额。最新请求优先。
2. 核实官方批次及岗位列表，记录查阅范围。不要把第一页或关键词搜索的结果当作全部岗位。
3. 对候选岗位读取完整 JD，检查毕业窗口、学历/专业、经验、城市、论文及申请限制。把硬门槛、优先项和可迁移能力分开。
4. 对照具体职责与个人证据，说明直接匹配、相邻经验、关键缺口和未知项；再进行相对排序。
5. 给出可执行的选择及官方链接，说明主要理由与风险。用户只剩一个名额时明确首选，不用一长串“都能投”代替决定。

通过率没有可靠统计时，不编百分比、HC、竞争人数或学校筛选规律。名额少、算法卷、测试开发稳等印象不能替代 JD 与候选人证据。优先项中的论文不等于硬性论文要求。

## 选择材料与经历

按实际职责选择简历，不能只看岗位名称。算法应用、金融科技服务端、通用软件、纯后端的材料重点可能不同；有公司定制版时先核对对应岗位及版本。

需要填写或定制材料时，从现有实习/项目中选择最相关的经历，简短说明选择理由；已有 `experience_bank.md` 时可复用，但不要求新建。结构化履历栏目按表单和用户要求填写，不因“重点展示”漏填必需经历。

允许调整顺序与强调重点，不允许新增工具、职责或成果。分清本人实现、团队指标、实验结果、发布准备与生产上线。缺少真实后端、前端或底层训练经验时，不靠包装制造匹配。

## 台账更新与复核

只有授权范围内的记录任务才写入。沿用现有系统，不自动创建第二套 CSV、数据库或看板。

- 使用用户指定的当前投递主档及已有同步机制，不以历史快照或模糊文件名匹配决定主档。
- 更新前重新读取最新记录，按公司、具体岗位/部门、岗位 ID、批次去重。状态应反映本次新证据；不能重复插入，也不能让旧截图将面试/终止状态退回“已投递”。
- 投递成功页面、明确已投递记录或用户确认是证据；按钮已点击、资料已保存不是。仅“流程终止”不足以推断在哪一轮被拒。
- 不编投递日、截止日、城市、拒绝原因或经历版本；截图精度就是记录精度。缺失值按原系统约定保留未知。
- 区分岗位线索和实际申请。授权记录线索时使用原系统的线索状态，不计入投递数量。
- 保留无关记录及既有进展。需要同步前端时遵循现有幂等机制，检查新增/修改数量与状态；没有查看实际页面，不能声称页面已刷新成功。
- 在授权范围内保留岗位链接、查阅时间、关键资格及必要 JD 内容，供后续面试准备；不要把分享链接里的个人 token 复制到公共资料。

有独立 `job_pool`/`application_log` 的系统才使用对应模板：前者存线索，后者存实际申请事件。`Submitted`、`Pending`、`Skipped`、`Needs user`、`Blocked` 不替换本地已存在的更细阶段。

新个人事实仅在用户授权维护资料时写回主档，附来源与日期；公司特定答案留在该公司的申请上下文。

## 网申及安全

网申前确认具体岗位、简历及可复用答案，先核对解析结果再补填。按 [网申操作](references/application-playbook.md) 批量填写与集中回读；推荐模式不读取这份操作手册。

验证、登录、敏感身份、缺失材料及权限问题按实际边界交接；不绕过网站控制，不切换工具规避拒绝。预览和暂存不等于提交许可。提交后以真实确认信息核实结果，再按授权范围更新记录。

涉及账户、验证码、隐私或公共分享时阅读 [安全边界](references/safety-and-boundaries.md)。本地个人资料、简历、申请历史与 token 不打包发布。只有用户要求监控时才设置持续任务，不因“没进展”自行轮询。
