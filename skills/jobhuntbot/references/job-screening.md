# 岗位筛选：证据、覆盖范围与相对可行性

用于推荐、比较、排序和“还有其他岗位吗”。默认只读；无需新建台账或打开申请表。顺序可按任务调整，但应解决下面这些判断问题。

## 1. 约束与历史

复用已确认的毕业年月、学历专业、实际经历、城市偏好、申请限制及投递历史。区分“看过”“推荐过”“已投”“终止”“当前在流程中”，不能因聊天提过公司就认定已投。同公司不同部门/岗位/批次分别看；有未结束申请时，先核实追加志愿规则，不建议用户随意撤回或覆盖。

用户说“只能再投一个”时，以机会成本比较，优先找主职责已有证据、硬缺口较少的岗位；不默认再冲一遍同类研究岗。用户只是不喜欢某城市，不升级成永久禁投；需要搬迁、轮班或出差时说明代价。

读取最新资料与最新记录，避免根据旧版本连续重复推荐已挂岗位。历史失败可以提醒减少同类重复尝试，但不能证明该领域完全不可行，更不能据此保证另一个领域通过率高。

去重针对具体申请实体，不针对整家公司。已终止同一申请不作为重复投递建议；不同岗位 ID、部门、批次或官方允许的重新申请可重新评估。

## 2. 查全候选范围，查深关键 JD

优先官方招聘列表和对应详情，必要时用网页检索补充入口、资格公告和截止时间。搜索摘要只能作线索，不作为完整 JD 的证据。

- 确认校招/社招/实习、批次、过滤条件与总条数；用户链接可能限制了类别、城市或页码。
- 分页、无限滚动、列表内部滚动均可能隐藏岗位。核对“总数”和已加载数量，不把首屏当全量。类别/关键词有遗漏风险时解除或扩展相关过滤。
- 不只搜 Agent：沿职责补查 AI 应用、业务算法、多模态、后训练、模型工程、数据闭环/质量、评测、Python 服务、金融科技等相邻方向。不要把整个算法或开发大类都当作同一种岗位。
- 先浏览相关范围的标题，再深读可能进入首选的岗位，既避免漏岗，也避免无目的逐一读取全部无关 JD。
- 用户质疑“只有这几个吗”时，优先补查尚未覆盖的分页、部门和类别，说明新增发现；不要只是重复旧推荐。
- 交付时准确表述范围，例如“已浏览 35 个标题，深读 8 个相关 JD”；不能说“查完全部岗位”而只看到 20/35 个。

若登录、失效或页面限制导致无法继续，说明已查范围和未核实项，给出暂定建议或让用户补截图；不绕过控制，不无限重试。

尚有相关岗位未加载时，可以给出“已查范围内首选”，不能下“只有这些适合”或“全站最佳”的结论。首选的硬资格未核实时保持条件性推荐，不建议直接占用唯一名额；次要加分项未知不必阻塞已足够有依据的选择。

## 3. 资格以具体版本为准

核对详情中的公司/部门、岗位 ID、地点、用工类型、批次及毕业窗口；正文与标题冲突时指出冲突。用当前日期判断 DDL，保留官方日期精度及时区；未知写“未查到明确截止”，不把截图汇总日期当官方确认。

- 社招同名岗有两年经验，不代表校招同名岗也有；不能跨版本套要求。
- 校招叫“高级工程师”不直接排除，先看真实经验门槛；“校园招聘”也不自动证明面向 2027。
- 留学生毕业窗口可能跨年份；根据实际月份判断，不能仅按届数。
- 早发布不等于过期，新发布不等于名额多。“申请”按钮存在仅证明页面可访问，不证明后台仍接收或有 HC。
- 校招优先资格有效、仍在招、匹配强及临近真实 DDL 的岗位，而非固定限定最近 24–48 小时。用户指定新发布岗位/社招时再使用相应时效筛选。
- 论文、学历、专业、工作年限、证书分别标记：硬要求、优先项、待核实。“有顶会论文优先”不能改成“必须有论文”。用户要求排除明确论文门槛时，排硬要求；论文加分仍可评估并说明劣势。
- 用户仅说“别要求论文”且范围含糊时，说明本次按排除硬门槛理解；若用户明确连“论文优先”也不要，则尊重更严格筛选，不用本规则覆盖其选择。
- “精通 Python/熟悉某框架”是能力要求，不能当作无关紧要；但与硬性毕业/专业资格性质不同，应通过具体工作证据判断缺口。

## 4. 对照职责，不做关键词投票

对首选岗位建立简短证据对照：JD 核心任务 → 具体实习/项目工作 → 证据强弱 → 缺口。至少解释对排序影响最大的匹配点和风险，不必展示每个技能词。

证据分类：

- 直接：做过相同或高度相近的任务，可说明方法、本人贡献与结果。
- 可迁移：有相邻方法/领域经验，但未做过该任务的关键环节。
- 缺少：现有资料不能支持，且是岗位的关键职责或技术要求。
- 待核实：资料不足或矛盾，需要补看记录；不是默认具备。

典型边界：框架使用不自动等于底层研发；批处理不等于在线生产服务；相邻领域经验只能作为可迁移证据。根据本人的真实资料逐项判断。

数据质量、无泄漏切分、冻结测试集、失败切片和模型回归是算法评测证据；它们与通用测试开发、人工标注管理、LLM 评测平台建设不同。用户说“没评测经历”时，用真实任务澄清具体是哪种，不强行声称全都做过。

不要只为“避卷”将业务算法经历降格为工具集成，也不要凭训练工具词包装成纯算法研究员。核对业务、训练/数据/评测/发布环节和工程主责。

## 5. 排序规则与职业代价

先排除确认不满足的硬条件及用户禁项。剩余岗位按当前目标比较：

1. 核心职责的直接证据与简历故事是否完整。
2. 关键缺口的数量、重要性及面试前能否合理补齐。
3. 已知考察方向与候选人能力是否相符，而非想象面试简单。
4. 用户的职业/地点接受度和有限申请名额。
5. 经证实的 DDL、岗位有效性和申请状态。

“通过可行性排序”是条件性相对判断，不是统计录用概率。缺少 HC、实际候选池和筛选标准时明确未知，不编百分比或精确匹配分。JD 更贴合只支持更有理由尝试，不支持“稳了”。“清北很多”“HR 瞎捞”“学历过滤”无可靠证据时不得作为事实。

算法、后端、数据平台、测试开发并非固定难度梯度。研究岗竞争可能强，但没有 Java/Go 服务经验的传统后端也可能更难。先看双方具体要求，再比较。

相邻方向须说明真实工作内容与代价：数据运营可能以现场采集、硬件排障、人员培训、轮班为主；技术支持可能偏交付、出差与客户沟通；模型部署可能是端侧 C++/TensorRT，而不是 Python 批推理。接受代价是用户的选择，不能用“更稳”掩盖方向转换。

## 6. 输出与复核

默认紧凑排序列表，列出少量有明显差异的岗位；用户只要一个，就明确一个首选，必要时一个条件性备选。

每个推荐包含：准确岗位名/部门或 ID、城市和批次、官方详情链接、对应真实经历、主要缺口，以及适用的选择条件。只在确有证据时列 DDL、论文门槛、名额限制。必要时以“优先尝试 / 冲刺 / 条件性备选 / 不建议”区分，不冒充录用概率。

说明结论为何相对其他候选更合理。简历版本可建议，但不未经请求改材料；不为清单好看补入不匹配的岗位。不把所有泛相关岗位都推荐投。

对拒绝的解释分开写“平台显示的阶段”和“可能原因”：简历筛选完成、测评已完成、部门筛选、流程终止不是同一件事；时间快不能证明自动筛简历，也不能证明学校、HC 或评测失败。

回答前检查：

- 是否漏了加载范围、用了社招 JD、认错年份或错读论文优先？
- 首选主职责有个人证据吗？是否隐藏领域/工程缺口或工作代价？
- 是否把试验、团队数字或结构有效率变成个人上线成果/准确率？
- 是否重复推荐已终止申请，或未经授权写了台账/打开投递流程？
- 链接、DDL、批次、剩余名额的确定程度是否与证据一致？
